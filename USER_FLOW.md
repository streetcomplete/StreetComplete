# StreetComplete — end-to-end user flow

All paths are relative to the repository root, read from the working tree on branch
`claude/streetcomplete-user-flow-hsh7md`. The running app described here is the **Android** app
(`app/src/androidMain` + `app/src/commonMain`);
`app/src/iosMain/kotlin/de/westnordost/streetcomplete/IosApp.kt` is currently only a developer
launcher for a handful of already-migrated screens, so no full iOS flow exists to document.

## Gaps

- **iOS flow.** `app/src/iosMain` contains only platform implementations plus `IosApp.kt`, a developer
  launcher that opens the changelog, credits and privacy screens. There is no iOS main screen, map,
  or quest flow in this repository, so nothing above describes iOS. Determining the intended iOS
  flow would need sources outside this repo (`MainScreen.kt` cites issue #6255 as the tracking issue
  for finishing the Compose migration).
- **Per-quest-type resurvey intervals.** Step 570 describes the mechanism, but the actual interval
  for any given quest is embedded in that quest type's `elementFilter` string; there are ~140 quest
  packages under `app/src/commonMain/kotlin/de/westnordost/streetcomplete/quests/`. I read
  `AddOpeningHours` as an example and did not enumerate the rest.
- **Individual quest forms.** I read the shared scaffolding (`QuestForm`, `YesNoQuestForm`,
  `QuestAnswerButtonBar`) and the container hosting them, not each of the ~140 quest forms. Steps
  240–270 therefore describe the common frame, not type-specific input behaviour (e.g. the
  opening-hours editor or the address form).
- **Persistence of the survey-confirmation "don't show again" toggle.** `SuppressSurveyConfirmation`
  in `MainBottomSheet.kt` is a private top-level `var`, i.e. in-memory for the process lifetime. I
  found no preference backing it, but did not exhaustively search `Preferences.kt` for an equivalent
  key.
- **Upload vs. download ordering under contention.** `Downloader` and `Uploader` share an injected
  `Mutex`, and each is its own WorkManager unique work chain (`"Download"`, `"Upload"`). Which runs
  first when both are pending is decided by WorkManager scheduling, which I did not trace.
- **Statistics backend semantics.** `StatisticsApiClientImpl` talks to a StreetComplete-operated
  service; what "rank", "days active" and "is analyzing" mean server-side cannot be determined from
  this repository.
- **Notification permission on Android 13+.** `SyncNotification.kt` and the manifest were not read in
  full, so what the user sees during a foreground sync when the notification permission is denied is
  not documented here.
